# Roadmap

This is the single place agentfab tracks future work. Every other doc in this tree describes the platform as it exists today; this one describes where it is going. When a roadmap item lands, its bullet moves out of this file and into the relevant architecture or reference doc.

## Elasticity and Scale

- Elastic autoscaling across pools of interchangeable instances of the same profile. The scheduler is already instance-aware and the control plane tracks per-node capacity, but there is no autoscaler that creates or retires instances based on load.
- Automatic mid-request resumption after a conductor takeover. The leader lease model supports a standby conductor taking over when the incumbent's lease expires. What is still open is picking up in-flight work mid-request; recovery currently marks interrupted requests and relies on the operator to retrigger them.
- Cross-cluster execution, where a single fabric spans multiple Kubernetes clusters or cloud regions with consistent control-plane state.

## Templates and Decomposition

- **Template parameterization for DAG-level fan-out (v0.3 headline).** Templates today are static — every task in `defaults/templates/*.yaml` is a concrete task with a fixed agent assignment. The kubelet demo (release 0.2.0) proved task-level fan-out works cleanly: one enumerated prompt produced 44 parallel developer tasks across 12 instances, with one architect synthesis at the end. The next generalization is the same pattern at the DAG level. Add a `parameters:` block to templates and a `for_each:` field on tasks so a template author can say "instantiate this task once per region in `[PJM, MISO, ERCOT, CAISO, SPP, NYISO, ISO-NE]` with `{region}` bound." The conductor's decompose pass expands the parameterized tasks into N concrete tasks at template-load time; the scheduler already handles N parallel tasks across M instances correctly (proven in kubelet); recovery semantics already work per-task. This unlocks any "same DAG, many scoped instances" workload: multi-region energy analysis, multi-codebase audit, multi-region cloud architecture review, multi-target drug-repurposing screen. Estimated scope: ~150 lines + tests across `internal/conductor/templates.go` (schema), a new template-expansion pass before decomposition, and a worked example. The us-energy-grid project's 5–7-ISO fan-out is the motivating use case and is currently waiting on this primitive.

## LLM Adapter

- ~~**Anthropic prompt caching via cache_control markers.** ALREADY IMPLEMENTED.~~ `internal/llm/provider.go` returns `claude.WithEnableAutoCache(true)` for every Anthropic model and wires it into all `MeteredModel` construction sites (conductor setup, conductor decompose, conductor chat, nodehost agent factory). Observed cache hit rates in production runs: 85% on Opus, 92% on Sonnet. The Eino claude adapter handles `cache_control: { type: "ephemeral" }` marking automatically against the longest cacheable prefix of each request.
- **Explicit cache breakpoints for reviewer-specific gains.** Anthropic's auto-cache marks the longest cacheable prefix; for reviewer invocations where the system prompt + upstream decision context is identical across 5–10 calls but the current working artifacts vary, manually-placed cache breakpoints could outperform auto by ensuring the stable prefix is always marked even when other request shape varies. Speculative additional gain on top of the existing 85–92% hit rate is small but measurable — worth profiling before committing engineering time.

## Storage

- Transactional backend for high-rate concurrent writes to shared profile state. The current file and etcd backends cover local and single-cluster distributed deployments. Multi-cluster fabrics with high write contention on the merged knowledge graph will want a stronger contract behind the same storage interface.
- **Content-addressable artifact URIs in task assignment messages.** The current shared-tier model is a per-agent filesystem snapshot copied from storage at workspace-open time. The synchronous Refresh-on-task-start and Sync-on-task-end barriers (the "Option B" mitigation, implemented in `internal/agent/agent.go`) close the cross-task race for current single-cluster deployments. The structurally correct long-term answer is to drop the filesystem-globbing convention entirely and pass explicit content-addressed artifact URIs (e.g. `shared://agents/<agent>/run-<id>/<file>@sha256:<hash>`) in task assignments. This gives immutability by construction, removes the snapshot-copy cost, and is required before serious multi-cluster work. See `storage-architecture.md` for the full design discussion.
- Per-dependency refresh on task start, so agents only re-materialize the specific upstream subtrees their task depends on rather than the entire shared tier. Performance optimization on top of the current Option B barrier; meaningful once any single shared tier grows past a few hundred MB.
- Live mount of the storage root for single-host topologies (local-bootstrap and kind). On topologies where every agent runs against the same physical filesystem, the per-agent snapshot is pure overhead; pointing `$SHARED_DIR` directly at the storage root eliminates both the materialize copy and the sync writeback. Kept separate from the multi-cluster path.

## Identity and Attestation

- First-class production certificate provider beyond the mounted-files path. The mounted provider is the current production-deployment shape; a first-class implementation that talks directly to SPIRE, a corporate workload CA, or another short-lived-certificate issuer is still open.
- Production bootstrap attestor that validates cloud-native bootstrap evidence (Kubernetes projected service account tokens, VM machine identity, cloud-managed workload tokens) outside the local development join-token path.
- External measured attestation validated outside the node binary. The control plane currently enforces measured claims (bundle digest, profile digests, binary digest) that the node presents about itself. Moving verification of those measurements outside the node process is the next step for hostile-runtime resistance.
- Subject-aware authorization across every distributed runtime surface. The control plane currently authorizes subject roles at admission and at node and instance registration. Extending the same subject-aware authorization to task dispatch, artifact writes, and every control-plane mutation API is still open.

## Pluggable Agent Implementations

- Config-level split between `AgentProfile` and `AgentImplementation`. Today an agent definition bundles the logical profile (name, purpose, capabilities, escalation policy, budgets) with the concrete native implementation contract (model, tools, prompt, tool loop). Splitting these into two nested concepts lets a profile point at one or more compatible implementation kinds.
- Native driver extracted as one implementation kind among several. The built-in agentfab loop becomes a plugin rather than the only execution path.
- Additional implementation kinds: externally hosted gRPC agents, containerized workers, customer-provided runtimes, and third-party agentic systems wrapped inside the agentfab harness.
- Explicit feature contracts so the Conductor and scheduler know which behaviors an implementation supports (peer review loops, checkpoint resume, knowledge curation, sandboxed tools) and degrade safely when an implementation does not support a feature.

## Deployment

- First-class in-tree Docker and Kubernetes runtime implementations. Both are supported deployment targets today and the deployment tooling lives outside the core runtime. Moving them in-tree is still open.

## Reliability and Failure Recovery

- **Per-call retry-with-checkpoint on LLM streaming failures.** The default LLM call timeout is 35 minutes (`internal/llm/meter.go:17`, after the bumps from the original 10m). When Anthropic's SSE stream stalls past that ceiling (observed three times in different sessions of the us-energy-grid dryrun: data-engineer, nuclear-strategist, viz-engineer), the whole task escalates and starts over with empty context — discarding 30–60 minutes of accumulated tool-loop progress. The fix is per-call retry rather than per-task: when a single SSE stream fails, the agent's tool-loop state (scratch files, accumulated context, previous LLM responses) should be preserved, and only the single failed inference should be re-attempted. Combined with per-tool-call checkpointing this would mean a 35-min stall costs at most one re-tried call, not a full task restart.
- **Per-agent (or per-scope) configurable LLM call timeout.** Today every agent's LLM calls share the single `defaultCallTimeout` constant. But analytical agents (grid-engineer, demand-forecaster) typically finish each call in 30–90 seconds, while code-generation agents (viz-engineer, sometimes data-engineer when producing large ETL scripts) legitimately need longer streaming windows because their output is multi-thousand-token HTML/JS/CSS. A single global timeout that satisfies viz-engineer over-allocates for analytical agents. Move the timeout into agent definition (`task_timeout` already exists at task level; add `llm_call_timeout` at the agent level), and let viz-engineer-style tasks get 45–60 minutes per call while analytical tasks stay at 10–15 minutes.
- **Soft-fabrication audit at framework level.** Each new failure surface (task_result prose, ARTIFACT_INDEX.md, viz hand-coded numbers, manifest_v1.json with claimed-but-missing files) has required a separate primer-level patch in the us-energy-grid project. The pattern is: agents fabricate when their work is mostly done but a small piece failed and they don't want to surface partial results. The framework-level fix is a `task_result` audit at the conductor: when an agent emits `task_result`, the conductor (or a dedicated lightweight checker) verifies every file the agent's summary claims to have produced actually exists on disk at the claimed path with at least the claimed size. Mismatch = task marked partial, triggers escalation rather than silent acceptance.

## Verification and Audit

- **Cross-agent numerical consistency audit.** Different agents in the same run sometimes produce different numbers for the same physical quantity — e.g., AI data center load by 2030 was 12.7 GW in one dryrun (data-engineer manifest) and ~7 GW in another (demand-forecaster top-down). No mechanism today reconciles these or even flags the discrepancy; downstream agents inherit whichever upstream they happened to read first. A `consistency-auditor` role (cheap, Haiku-based, runs in parallel after analytical agents finish) cross-references each named quantity across all upstream artifacts and flags conflicts for the conductor or scientific-reviewer to arbitrate before narrative-editor synthesizes. Could be a per-quantity assertion file (e.g., "ERCOT 2030 peak demand: X GW") that every analytical agent contributing the quantity writes a row to, and the auditor flags any row that diverges from the others beyond a stated tolerance.
- **Reviewer disk-state verification.** Today `scientific-reviewer` reviews an agent's task_result *prose* without independently verifying that the claimed files exist on disk at the claimed paths with the claimed contents. The us-energy-grid dryrun caught multiple cases where agents soft-fabricated success in their task_result text. Extension: scientific-reviewer's primer + tool capabilities should require a `ls -la` + `wc -l` / `head` check on every file the agent claims to have produced, with the reviewer's verdict explicitly noting whether each claimed file was found. Probably ~20 lines in the primer + an enforcement rule in the loop FSM.

## Operator Experience

- **TUI debug-log integration.** With `--debug` enabled, slog output goes to `os.Stderr`, but the TUI takes over the terminal with ANSI control sequences, so the debug stream is hidden or scrolled away. Operators currently work around this by redirecting `2> /tmp/agentfab-stderr.log` and tailing in a second terminal. A dedicated debug-log panel inside the TUI (toggleable hotkey, scrollable) or a `--debug-file <path>` flag that's well-documented in the README would close this UX gap without forcing the redirect dance.
- **Strict template-adherence mode.** The conductor's decompose pass is LLM-based and occasionally re-introduces tasks that the user prompt explicitly says not to add — most reliably observed with the dropped `t10` publication step in the us-energy-grid dryrun template, which the conductor re-added on two separate runs despite explicit "do not introduce a publication step" directives in the prompt. A strict-template mode (`--template-mode strict` or `template.strict: true` in YAML) would skip the LLM decompose pass entirely when a template matches and just dispatch the template's literal task list. Loses some adaptability for atypical user prompts but eliminates the "conductor reinterprets the template" failure surface for production runs.
- **Code-generation vs analytical-reasoning task affordance.** The viz-engineer's working shape — generate a 30 KB HTML file with embedded JS via heredoc-style shell writes — is fundamentally different from an analytical agent's "reason through grid resource adequacy" shape. Code-generation tasks need: more iteration budget, longer per-call LLM streaming windows, output-token caps tuned for code (not prose), and probably a different review loop (build-verifies-locally rather than methodology-review). Folding this back into agent definitions as a `task_kind: code_generation | analytical_reasoning | data_ingestion` enum that tunes scope defaults would let the platform serve both well without separate one-off configuration.
